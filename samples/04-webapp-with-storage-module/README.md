# Step 4: Azure Web App with a modular storage component

This sample introduces Bicep modules and shows how a deployment can be broken into smaller, reusable building blocks.

## What you will learn

- how to create a reusable Bicep module
- how to pass values into a module
- how to consume module outputs in another resource
- how a web app can read values generated by a storage deployment

## Files in this sample

- `main.bicep` - the main deployment that composes multiple resources
- `main.bicepparam` - parameter values used for the sample
- `modules/storage-with-container.bicep` - a reusable module for the storage account and container
- `deploy-cli.sh` - Azure CLI deployment example
- `deploy.ps1` - PowerShell deployment example

## Deployment flow

The main template calls a small module that creates the storage account and blob container. Once that module is complete, the main template creates an App Service plan and a web app. The web app receives values from the module, such as the storage account name and container name, through its application settings.

## Deploy with Azure CLI

```bash
az login
az group create --name rg-bicep-lab --location eastus
az deployment group create \
  --resource-group rg-bicep-lab \
  --template-file ./main.bicep \
  --parameters ./main.bicepparam
```

## Deploy with PowerShell

```powershell
az login
az group create --name rg-bicep-lab --location eastus
az deployment group create `
  --resource-group rg-bicep-lab `
  --template-file ./main.bicep `
  --parameters ./main.bicepparam
```

## Challenge

Open the module file and change the storage container name. Then redeploy and confirm the web app settings still reflect the module output values.

## Why modularity matters

A small Bicep module can be reused across many deployments instead of copying the same resource block into every template. This makes the code easier to read, easier to maintain, and simpler to share across teams.
